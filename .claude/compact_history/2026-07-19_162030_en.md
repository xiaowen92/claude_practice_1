## Observe (key understanding of Claude Code / LLM underlying logic)

1. **The `stop_sequences` parameter is silently dropped at the gateway layer, not an SDK or code logic issue**:
   - Verified via `client.messages.with_raw_response.create()` that the Anthropic SDK does correctly write `stop_sequences` into the outgoing HTTP request body.
   - But in the response actually received, `stop_reason` is always `end_turn`, never `stop_sequence`, and the `stop_sequence` field is always `None` — even in the simplest case (`stop_sequences=["5"]` asking the model to count from 1 to 10), it has no effect at all.
   - Root cause traced to the internal gateway pointed to by the `ANTHROPIC_BASE_URL` environment variable — this internal gateway does not correctly forward/handle the `stop_sequences` parameter, which falls into the known issue category of "enterprise internal LLM gateways with incomplete support for Anthropic API parameters" (external corroboration: LiteLLM repository issue #33075, describing a similar `stop_sequences` forwarding defect — though that case raises an error rather than silently ignoring the parameter).
   - **Implication**: any code that relies on `stop_sequences` to guarantee clean output truncation (e.g., this notebook's use of `"```"` as a stop sequence to get clean JSON) is unreliable in this gateway environment — the model may continue generating arbitrary content afterward, so whether `json.loads()` raises an error is purely down to luck; `json.JSONDecoder().raw_decode()` is the more robust parsing approach in this environment.

2. **The Model grader (LLM-as-judge) scoring mechanism is fundamentally a holistic judgment, not a weighted calculation**:
   - Without a rubric or criteria, the model makes a one-shot holistic judgment against `<task>` and `<solution>` and directly outputs a number from 1-10 — with no explicit rules or weights; the same solution may receive a different score on a different run (especially with `temperature=1.0`).
   - Adding `solution_criteria` narrows the judgment dimensions of "what counts as correct" from free-form model interpretation to concrete checkpoints, reducing the interpretive slack in the task description itself.
   - Adding a rubric narrows "what score to give" from model intuition to "select against fixed tier descriptions," which improves reproducibility, but **the score is still a single judgment produced by the model in one pass, not computed from sub-scores via a formula** — this is why a rubric is not the same as mathematical weighting.
   - **The actual definition of mathematical weighting**: there must be independent sub-scores (e.g., each criterion judged pass/fail individually), then a deterministic formula (`weighted_score = Σ(sub_score * weight) / Σ(weight)`) computes the final score. Sub-scores can come from model judgment, but the "aggregate into a final score" step must be computed by code — it cannot be handed back to the model to "consider holistically."
