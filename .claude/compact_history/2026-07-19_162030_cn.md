## Observe（关于 Claude Code / LLM 底层逻辑的关键理解)

1. **`stop_sequences` 参数在 gateway 层被静默丢弃,而不是 SDK 或代码逻辑的问题**:
   - 用 `client.messages.with_raw_response.create()` 验证过,Anthropic SDK 确实把 `stop_sequences` 正确写进了发出的 HTTP request body。
   - 但最终收到的 response 里,`stop_reason` 永远是 `end_turn`,从未变成 `stop_sequence`,`stop_sequence` 字段始终是 `None`——即使是最简单的 case(`stop_sequences=["5"]` 让模型数 1 到 10)也完全不生效。
   - 根因定位在环境变量 `ANTHROPIC_BASE_URL` 指向的内部 gateway——这个内部 gateway 没有正确转发/处理 `stop_sequences` 参数,属于"企业内部 LLM gateway 对 Anthropic API 参数支持不完整"这一类已知问题(外部佐证:LiteLLM 仓库 issue #33075,描述类似的 `stop_sequences` 转发缺陷,只是那个 case 是报错而不是静默忽略)。
   - **推论**:任何依赖 `stop_sequences` 保证输出干净截断的代码(比如这个 notebook 里用 `"```"` 做 stop sequence 来拿干净 JSON),在这个 gateway 环境下都不可靠——模型可能会继续往后生成任意内容,`json.loads()` 是否报错完全是运气,`json.JSONDecoder().raw_decode()` 才是这种环境下更稳健的解析方式。

2. **Model grader(LLM-as-judge)打分机制的本质是 holistic judgment,不是加权计算**:
   - 没有 rubric、没有 criteria 时,模型是对着 `<task>` 和 `<solution>` 做一次性整体印象判断,直接给出 1-10 的数字——没有任何显式规则或权重,同一个 solution 换一次 run(尤其 `temperature=1.0`)可能打出不同分。
   - 加 `solution_criteria`,是把"什么算对"的判断维度从模型自由发挥收窄成具体检查点,减少 task 描述本身的解释空间。
   - 加 rubric,是把"打几分"从"模型直觉"收窄成"对照固定档位描述选择",复现性会提升,但**score 依然是模型一次性给出的单一判断,不是通过公式从子分数算出来的**——这就是为什么 rubric ≠ 数学加权。
   - **数学加权的真正定义**:必须有独立的子分数(比如每条 criteria 单独判断 pass/fail),再用确定性公式(`weighted_score = Σ(sub_score * weight) / Σ(weight)`)算出最终分数。子分数可以来自模型判断,但"汇总成最终分数"这一步必须是代码算出来的,不能再交给模型"综合考虑一下"。
