## Observe (key understanding of Claude Code / LLM underlying logic)

1. **Standard tool use is a "four-step back-and-forth between you and the model" — the model does not execute your function itself**:
   - Step 1 (you): `user` asks
   - Step 2 (model): `assistant` returns `[ToolUseBlock(...)]`, `stop_reason: tool_use` — the model only "tells you which tool to execute", it does not actually run it
   - Step 3 (you): actually execute the function in Python, wrap the result in a `tool_result` block, and put it into a `user` message to send back
   - Step 4 (model): reads the tool result, `assistant` generates the final natural-language answer
   - Skipping Step 3 and jumping straight to Step 4, the API returns a 400 saying "tool_use is missing a following tool_result".

2. **`tool_result` is a content block and must be wrapped in a `content: [...]` list**, not laid out at the outermost level of the message. The API recognizes it via the block's `"type": "tool_result"`; the field names (`type` / `tool_use_id` / `content` / `is_error`) are fixed by the spec, and `tool_use_id` must equal the `id` of the `ToolUseBlock` from Step 2, otherwise it errors.

3. **The number and types of blocks in `response.content` are decided dynamically by the model each turn** — you can't assume `content[0]` is always text or always tool_use — you should iterate over `content` and dispatch on `block.type`. Hard-coding by position (like `content[0].text`) will hit an `AttributeError` when the block type doesn't match.

4. **Whether a tool's `input` is empty is determined by the schema, unrelated to the model version**: `required: []` + a default → the model passes `{}`; a required parameter → the model must fill it.
